CerviGrade · Product phase plan

Case lifecycle, usage metering and the Integration Centre

The research is sound, and the three capabilities really are one problem. But five things in the current codebase change how it has to be built, and one of them changes the order.

What the code actually looks like today

GapNo episode identifiers exist anywhere

BatchReviewItem carries nhi, externalPatientId, receivedDate and rowNumber. There is no accession number, specimen ID or message control ID, and no per-item source system — sourceSystem sits on BatchRun, one level up. SourceMetadata has no slot for them, the template columns do not define them, and no adapter parses them. The fingerprint inputs have to be built before anything can be fingerprinted.

GapThere is no Organisation model

organisationKey is a nullable free-text string on RuleSetActivation alone, used only to scope which ruleset is active. Nothing else in the schema is tenant-scoped, and GPPractice is a referrer rather than a customer.

BlockerDuplicate detection is not demonstrable yet

realistic-dataset.ts defines six deliberate RETURNING_PATIENTS with fixed NHIs — a good seed. But every generated case gets caseId: crypto.randomUUID(), so each pull mints brand-new identity. Until the generator emits stable episode keys, “48 new · 12 already in review” can never appear on screen.

ConstraintHL7 v2 MLLP cannot run on this host

MLLP is a persistent TCP listener. This deploys to Vercel serverless functions, which cannot hold a socket open. FHIR and PMS polling are feasible — vercel.json already declares a cron — but an HL7 v2 feed needs a separate long-running ingestion service. That is an infrastructure decision, and it should be settled before the HL7 connector is designed.

Fits“Updated result” lands on machinery that already exists

RuleEvaluation already has previousEvaluationId, subsequentEvaluations and regradeReason, plus CaseAuthorityPin so an existing case keeps its original authority. An updated episode is a regrade, and the chain is already there.

Migration hazard

RuleEvaluation cannot be backfilled. Its immutability trigger is BEFORE UPDATE with no column list, so every update aborts. Adding a column is fine; populating existing rows is impossible. Derive organisation through batchRunId / caseId and leave the immutable table alone.

One change to the running order

The research lists the organisation model fourth. It has to be first. Episode fingerprints include the source organisation; usage events are billed per organisation; integration connections are configured per organisation. Each capability writes rows that are meaningless without a tenant — and two of those tables are append-only by design, so a tenant added later cannot be backfilled onto the history the pilot generates.

  1. Organisation scope moved from 4th

    One small model, reusing the organisationKey values that already exist so organisation-scoped rulesets keep working untouched.

  2. Episode identity and lifecycle

    Two-tier fingerprint, an observation record for every arrival, and the identifiers threaded through every layer that produces a case.

  3. Usage ledger

    Immutable, append-only, with a closed reason vocabulary. Built now; priced later.

  4. Integration Centre — a, then b

    3a configuration, health and audit: ordinary product work. 3b credentials and live connection tests: blocked on a security decision that has not been made.

Vocabulary fix, before it is baked into every table

The research uses “organisation” for two different parties: the customer whose usage is billed, and the source facility the data came from. A lab sends results to a service; they are not the same. Organisation is the tenant; the origin stays as sourceSystem / sourceFacility on the episode.

Phase 1 · The two-tier key, and why only one may act

The research proposes one fingerprint. It needs to be two, because they carry very different confidence and must have very different consequences.

KeyCompositionMay classify as
Strong hash(organisationId, sourceSystem, sourceEpisodeKey) — accession, specimen or message control ID. Deterministic. In review · Completed · Updated
Weak hash(organisationId, nhi, testType, collectionDate) — a heuristic. Possible duplicate only — advisory, never withholding
Clinical safety, not a nicety

Suppressing a screening result on a fuzzy match is how a real result gets lost, and the same patient legitimately has repeat tests, surveillance results and amended reports. A weak match must never withhold a case. It stays selectable and the reviewer decides.

Nothing arrives and disappears

Every arrival gets an EpisodeObservation, including the ones that are correctly not reprocessed. Otherwise a suppressed result is indistinguishable from a lost one — which is exactly the failure a hospital will ask about. 

model EpisodeObservation {
  episodeId         String
  batchRunId        String
  classification    EpisodeClassification
  batchReviewItemId String?   // null when not processed
  outcome           String    // "not reprocessed — completed 12 Aug"
  payloadDigest     String    // detects genuinely changed content
  observedAt        DateTime
}

payloadDigest is what separates a true duplicate from an updated result: same strong key, different digest means new clinical information — and that becomes a regrade on the existing evaluation chain, with the prior decision preserved.

Lifecycle, without re-implementing what exists

RECEIVED → VALIDATED → ROUTED → EVALUATED → IN_REVIEW → REVIEWED → COMPLETED
side states: DUPLICATE · UPDATED · FAILED_IMPORT

NEEDS_INFORMATION is deliberately not a lifecycle state. It is already a BatchReviewDisposition set by a reviewer. Duplicating it would create two sources of truth for one fact, and they would drift. Lifecycle is where a case sits in the pipeline; disposition is what a clinician decided.

What has to change to carry the identifiers

  • SourceMetadata — add sourceEpisodeKey, sourceFacility, testType, collectedOn.
  • template-columns.ts — add accession/specimen columns with aliases. This file drives both validation and the generated template, so both follow automatically.
  • The three file adapters — parse the new columns.
  • BatchReviewItem — add episodeId.
  • Both demo generators — emit stable episode keys. Give the six returning patients fixed accession numbers so a second pull genuinely re-presents the same episodes, and change one result so UPDATED appears too.

Classification runs in the preview path, which already returns an un-persisted preview — so the counts can appear on Pull Cases before anything is committed. The episode rows are written at persistence time.

Phase 2 · Usage ledger

Two decisions the schema encodes, both hard to change afterwards:

  • billableReason is a closed enum, not free text. An invoice dispute is answered by reading that column, and free text cannot be aggregated or audited.
  • Corrections append. Give the ledger the same immutability triggers as RuleEvaluation — the pattern and its tests already exist. A wrongly-billed event is corrected by appending a reversal that points at it, never by editing. A billing ledger you can quietly edit is not evidence.

isDemo reuses the existing demoProvenance() helper, so demo traffic is excluded by the same mechanism that already keeps demo attestations out of production governance gates. The Usage & Activity screen reports from this ledger only — never by counting BatchReviewItem or RuleEvaluation rows. Build the write path now and leave prices off the screen; the write path is the expensive thing to retrofit.

Phase 3 · Integration Centre

CONNECTOR_CATALOG stays as the catalogue of connector types; new IntegrationConnection rows are the configured instances. The wizard runs Connection → Authentication → Mapping → Test → Schedule → Activate, and the state machine only permits ACTIVE from MAPPING_VERIFIED.

Test Connection is worth building in 3a even with no network access, because most of its value is offline: required-field coverage, mapping completeness (14/16 mapped), schedule validity, and a clear Ready for activation: NO. The live network checks land in 3b.

Recommended: store a reference, never a value

credentialRef holds the name of an environment or secret-manager entry; the value is set in the platform environment and read server-side at call time. The application database then never contains a credential — so a dump, a backup, an audit export or a stray Prisma query cannot leak one. Encrypting secrets at rest instead needs a key management story (where the key lives, how it rotates, who can read it) that this stack does not have yet; that is the wrong first move for a pilot.

Either way the UI rule holds and should be enforced by tests: Replace credential and Test connection, never Show credential. The audit payload must be built from an allow-list of fields, the way the user-audit helper already is — never by serialising the whole config object, which is how a credential ends up in an audit record.

Sizing and risk

PhaseSizeMain risk
0 · OrganisationSmallTouching many queries at once — mitigated by doing it before there is history to migrate
1 · Episode identityLargeThe identifiers exist nowhere yet: schema, template, three adapters, both demo generators, preview and persistence all change together
2 · Usage ledgerMediumGetting the reason vocabulary right first time — the ledger is immutable
3a · Integration configMediumRedaction discipline in the audit payload
3b · CredentialsMediumBlocked on the secret-storage decision; HL7 additionally blocked on hosting

Phase 1 is the one most likely to be underestimated. The classification logic is straightforward; threading a new identifier through every layer that produces a case is not, and the demo generators must change or the feature is invisible.

Decisions needed before Phase 2 and 3b

  1. Is an updated-result re-evaluation billable? Same episode, new clinical information, a second governed evaluation and a second clinician review. Defensible either way — but it is a pricing decision, not an engineering one, and it must be settled before the reason vocabulary is fixed, because the ledger is immutable.
  2. Secret storage: environment/secret-manager reference (recommended), or encrypted at rest with a managed key.
  3. HL7 v2 ingestion host: is a long-running service in scope for the pilot, or does the pilot run on file upload and FHIR only?
  4. Does one deployment ever serve more than one customer? If single-tenant forever, Phase 0 shrinks to a seeded constant. If not, it is load-bearing.

What this deliberately does not touch

No clinical rule, no ruleset content, no evaluation logic, no authority resolution, no case pinning, no review-queue decision logic, no safety stop, no governance enforcement, no audit immutability. Episode classification runs strictly before evaluation and decides only whether a case is presented for processing; an updated episode enters the existing regrade chain rather than creating a new one. The clinical layer stays as it is.
